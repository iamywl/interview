## 2021 · 오픈소스 · 개발자 생태계

### 1. 그해 핵심 트렌드
2021년 오픈소스 생태계는 두 개의 큰 축으로 움직였다. 첫째는 **AI 코딩 보조 도구의 등장**으로, 6월 GitHub Copilot 기술 프리뷰가 공개되며 LLM 기반 코드 자동완성 시대가 열렸다. 둘째는 **오픈소스 공급망 보안의 위기**로, 12월 Apache Log4j의 Log4Shell(CVE-2021-44228) 취약점이 전 세계 인프라를 강타하며 "오픈소스 의존성 관리"가 보안의 핵심 의제로 부상했다. 동시에 Elastic이 라이선스를 SSPL/Elastic License로 변경하고 AWS가 이를 OpenSearch로 포크하면서, 클라우드 사업자와 오픈소스 벤더 간 **라이선스 전쟁**이 본격화됐다.

### 2. 대표 뉴스·사건
- **GitHub Copilot 기술 프리뷰 공개**: 2021년 6월 29일 GitHub가 OpenAI Codex 기반 AI 페어 프로그래머 Copilot의 기술 프리뷰를 발표했다. Python·JavaScript·TypeScript·Ruby·Go에서 줄 단위·함수 단위 코드 자동완성을 제공했다 ([GitHub Blog, 2021-06-29](https://github.blog/news-insights/product-news/introducing-github-copilot-ai-pair-programmer/)).
- **Elastic 라이선스 변경**: 2021년 1월 Elastic이 Elasticsearch·Kibana의 라이선스를 Apache 2.0에서 SSPL과 Elastic License 이중 라이선스로 전환했다. AWS의 무임승차 관리형 서비스를 막으려는 목적이었다 ([InfoQ, 2021-01](https://www.infoq.com/news/2021/01/elastic-aws-open-source/)).
- **AWS OpenSearch 포크**: 2021년 4월 AWS가 Elasticsearch·Kibana 7.10.2를 Apache 2.0으로 포크한 OpenSearch를 출시했다. 오픈소스 커뮤니티가 Elasticsearch와 OpenSearch로 양분됐다 ([InfoQ, 2021-04](https://www.infoq.com/news/2021/04/amazon-opensearch/)).
- **Log4Shell 취약점(CVE-2021-44228)**: 2021년 12월 Apache Log4j에서 원격 코드 실행 취약점이 발견됐다. Apache가 CVSS 최고점 10점을 부여했고, CISA 국장은 "경력상 가장 심각한 취약점 중 하나"라고 평가했다 ([Wikipedia, 2021-12-10](https://en.wikipedia.org/wiki/Log4Shell)).
- **Log4Shell 전 세계 확산**: 2021년 12월 14일 기준 전 세계 기업 네트워크의 약 절반이 실제 탐지 시도를 받았고, 24시간 내 60종 이상의 변종 익스플로잇이 만들어졌다 ([Wikipedia, 2021-12-14](https://en.wikipedia.org/wiki/Log4Shell)).
- **CNCF 프로젝트 졸업 확대**: 2021년 OPA(Open Policy Agent)가 2월, Linkerd가 7월 CNCF 졸업 프로젝트가 됐다. CNCF 연례 설문에서 조직의 96%가 쿠버네티스를 사용·평가 중이라고 답했다 ([CNCF, 2021](https://www.cncf.io/reports/cncf-annual-survey-2021/)).

### 3. 핵심 기업·제품·기술 키워드
- **AI 코딩**: GitHub Copilot, OpenAI Codex
- **라이선스**: SSPL, Elastic License, Apache 2.0, OpenSearch 포크
- **공급망 보안**: Log4Shell, CVE-2021-44228, SBOM(소프트웨어 자재명세서), 의존성 스캔
- **클라우드 네이티브**: CNCF, Kubernetes, OPA, Linkerd, Prometheus
- **거버넌스**: Linux Foundation, Apache Software Foundation, OpenSSF(이듬해 본격화 기반)

### 4. 시장 수치·전망
- Synopsys 2021 보고서 기준 기업 소프트웨어 프로젝트의 98%가 오픈소스 코드를 포함하며, 평균 애플리케이션 코드의 75%가 오픈소스로 추정됐다 ([Data Center Knowledge, 2021](https://www.datacenterknowledge.com/open-source-software/log4shell-vulnerability-highlights-software-supply-chain-issues)).
- CNCF 설문 기준 쿠버네티스 사용·평가 조직 비율 96%(전망 아닌 설문 수치) ([CNCF, 2021](https://www.cncf.io/reports/cncf-annual-survey-2021/)).
- Log4Shell의 잠재 피해는 "산정 불가" 수준으로 평가됐다(추정) ([Wikipedia, 2021](https://en.wikipedia.org/wiki/Log4Shell)).

### 5. 전년 대비 변화점
- **새로 뜬 것**: LLM 기반 AI 코딩 보조 도구(Copilot), 오픈소스 공급망 보안 의제, 클라우드 사업자 대응 라이선스(SSPL 채택 확산).
- **식은 것**: "오픈소스 = 무조건 Apache/MIT" 식 단순 인식. 클라우드 무임승차 논쟁으로 순수 퍼미시브 라이선스에 대한 벤더의 신뢰가 약화됐다.

### 6. PT 발표 주제 후보
- **Log4Shell이 바꾼 오픈소스 공급망 보안**: 단일 로깅 라이브러리 취약점이 어떻게 전 세계 인프라를 위협했고, SBOM·의존성 관리가 왜 필수가 됐는가.
- **오픈소스 라이선스 전쟁의 서막**: Elastic의 SSPL 전환과 AWS OpenSearch 포크가 보여준 오픈소스 비즈니스 모델의 한계.
- **AI 페어 프로그래머의 등장**: GitHub Copilot이 연 코드 생성 자동화 시대와 개발자 생산성 논쟁.

### 7. 예상 꼬리질문 + 답변 포인트
- **Q. Log4Shell 같은 공급망 취약점을 어떻게 탐지·방어할 수 있나?**
  A. 정적으로는 SBOM과 의존성 스캐너로 취약 버전을 식별한다. 다만 정적 분석은 실제 악용 여부를 놓칠 수 있어, 런타임에서의 동적 관측이 보완책이 된다. 제 경험상 시스템 콜을 동적으로 관측해 비정상 행위(예: 예기치 않은 외부 연결, 자식 프로세스 생성)를 탐지하면, 알려지지 않은 익스플로잇도 행위 기반으로 잡아낼 수 있다.
- **Q. 컨테이너 환경에서 Log4Shell 같은 RCE를 막으려면?**
  A. 컨테이너 격리만으로는 부족하다. 최소 권한 원칙, egress 네트워크 정책으로 LDAP/외부 호출을 차단하고, seccomp·eBPF로 시스템 콜 수준에서 비정상 호출을 모니터링한다. 제가 다룬 컨테이너 보안 관점에서 보면, 이미지 빌드 시점의 취약점 스캔과 런타임 이상탐지를 함께 써야 한다.
- **Q. 오픈소스 라이선스 변경이 개발자에게 주는 실무적 영향은?**
  A. SSPL은 OSI 승인 오픈소스가 아니어서, 관리형 서비스 제공이나 재배포에 제약이 생긴다. 의존성에 라이선스 변경이 발생하면 포크(OpenSearch)로의 마이그레이션 비용과 법적 리스크를 검토해야 한다. 풀스택 개발자로서 의존성의 라이선스 추적은 코드 품질만큼 중요한 관리 항목이라고 본다.
