## 실시간 데이터 플랫폼 (realtime)

### 1. 한 줄 정의와 큰 그림 (무엇을 푸는 기술/이슈인가, 왜 중요한가)

실시간 데이터 플랫폼이란, 데이터가 발생하는 즉시 혹은 거의 즉시 수집하고 처리하여 의미 있는 결과를 만들어내는 기술의 총체입니다. 과거처럼 데이터를 모아서 한꺼번에 처리하는 '배치(Batch) 처리' 방식과 달리, 데이터의 흐름, 즉 '스트림(Stream)'을 멈추지 않고 연속적으로 분석하여 '지금 이 순간' 일어나는 일에 바로 대응할 수 있게 해주는 것이 핵심입니다.

이것이 왜 중요하냐면, 비즈니스의 속도가 빛의 속도처럼 빨라졌기 때문입니다. 예를 들어, 고객의 카드 부정사용이 의심될 때, 하루 뒤에 분석해서 알려주면 이미 늦습니다. 결제 버튼을 누르는 순간, 그 패턴을 분석해서 1초 안에 사기인지 아닌지 판단해야 피해를 막을 수 있습니다. 이렇게 즉각적인 의사결정과 대응이 기업의 경쟁력을 좌우하는 시대이므로, 실시간 데이터 플랫폼은 이제 선택이 아닌 필수가 되어가고 있습니다.

### 2. 핵심 개념·용어 정의 (하향식, 충분히 많이)

-   **데이터 스트림 (Data Stream):** 끊임없이 생성되고 흐르는 데이터의 연속적인 흐름입니다. 수도꼭지에서 물이 계속 흘러나오는 것처럼, 센서 데이터, 로그, 주식 거래 정보 등이 시간 순서에 따라 계속해서 시스템으로 들어오는 것을 말합니다.

-   **이벤트 (Event):** 데이터 스트림을 구성하는 하나하나의 데이터 조각입니다. '오후 3시 5분에 A 고객이 B 상품을 클릭했다'와 같이, 특정 시간에 발생한 상태의 변화나 행위를 기록한 데이터를 이벤트라고 부릅니다. 실시간 데이터 처리의 가장 기본적인 단위입니다.

-   **스트림 처리 (Stream Processing):** 데이터 스트림을 실시간으로 처리하고 분석하는 기술입니다. 데이터가 저장장치에 기록되기 전에, 메모리 위에서 바로 계산하여 결과를 도출하는 방식입니다.

-   **소스 (Source):** 데이터 스트림이 시작되는 곳입니다. 웹 서버의 로그, IoT 기기의 센서, 모바일 앱의 사용자 클릭 데이터, 데이터베이스의 변경 기록(CDC, Change Data Capture) 등이 소스가 될 수 있습니다.

-   **싱크 (Sink):** 처리된 결과가 최종적으로 저장되거나 전달되는 곳입니다. 분석 결과를 저장하는 데이터베이스, 시각화 대시보드, 다른 시스템으로 이벤트를 보내는 메시징 큐 등이 싱크가 됩니다.

-   **메시지 큐 (Message Queue):** 데이터를 보내는 시스템(Producer)과 데이터를 받는 시스템(Consumer) 사이의 중간 다리 역할을 하는 소프트웨어입니다. 대량의 데이터가 몰려도 시스템이 다운되지 않도록 버퍼 역할을 해주고, 데이터가 유실되지 않도록 보장합니다. 대표적으로 **Apache Kafka**, **AWS Kinesis**가 여기에 속합니다.

-   **스트림 처리 엔진 (Stream Processing Engine):** 실제 스트림 데이터를 분석하고 연산하는 로직을 수행하는 소프트웨어입니다. **Apache Flink**, **Apache Spark Streaming**, **Kafka Streams** 등이 대표적입니다.

-   **윈도우 (Window):** 끝없이 이어지는 데이터 스트림을 분석하기 위해, 특정 시간이나 개수 단위로 데이터를 묶어주는 논리적인 단위입니다.
    -   **텀블링 윈도우 (Tumbling Window):** "매 1분마다"처럼, 시간이 겹치지 않게 스트림을 나누는 창입니다.
    -   **슬라이딩 윈도우 (Sliding Window):** "최근 1분간"처럼, 특정 시간 간격으로 계속 움직이면서 스트림을 바라보는 창입니다. 윈도우끼리 시간이 겹칠 수 있습니다.
    -   **세션 윈도우 (Session Window):** 사용자의 활동을 기반으로 윈도우를 정합니다. 예를 들어, 5분 동안 아무 클릭이 없으면 하나의 '세션'이 끝났다고 보고 윈도우를 닫습니다.

-   **상태 저장 처리 (Stateful Processing):** 스트림을 처리할 때 이전의 처리 결과를 기억하고 현재 데이터 처리에 활용하는 방식입니다. 예를 들어, '한 사용자가 1분 동안 몇 번이나 클릭했는가'를 계산하려면, 이전 클릭 횟수를 '상태'로 저장하고 있어야 합니다. **Apache Flink**가 상태 저장 처리에 매우 강력한 기능을 제공합니다.

-   **워터마크 (Watermark):** 네트워크 지연 등으로 이벤트가 순서대로 도착하지 않을 때, '이 시간까지의 데이터는 모두 도착했을 것'이라고 시스템에 알려주는 기준선입니다. 이 기준선을 넘어서는 너무 늦은 데이터는 처리를 포기하거나 별도로 처리하게 하여, 전체 시스템의 지연을 막습니다.

### 3. 동작 원리·구조 (단계별로 자세히)

실시간 데이터 플랫폼은 크게 세 단계로 이루어집니다.

1.  **데이터 수집 (Ingestion):**
    -   다양한 **소스**에서 생성된 **이벤트**들이 **메시지 큐**(예: Apache Kafka)로 흘러 들어옵니다. Kafka는 대용량의 스트림 데이터를 안정적으로, 그리고 순서를 어느 정도 보장하며 받아주는 역할을 합니다. 여러 '프로듀서(Producer)'가 각자의 데이터를 Kafka의 특정 '토픽(Topic)'에 발행(Publish)하면, 데이터는 일단 안전하게 저장됩니다. 이 과정은 마치 여러 우체국에서 온 편지들을 거대한 중앙 우편물 분류 센터로 모으는 것과 같습니다.

2.  **데이터 처리 (Processing):**
    -   **스트림 처리 엔진**(예: Apache Flink)이 Kafka에 쌓인 데이터를 구독(Subscribe)하여 실시간으로 가져와 처리합니다. 개발자는 Flink에 "A 토픽에서 데이터를 가져와, 5분 단위 **윈도우**로 묶고, 데이터를 특정 기준에 따라 필터링한 후, 건수를 세어서 결과로 만들어라" 와 같은 처리 로직(Job)을 작성하여 실행시킵니다.
    -   만약 **상태 저장 처리**가 필요하다면, Flink는 계산 중간 결과를 자체적인 상태 저장소(State Backend)에 저장합니다. 예를 들어, 사용자별 마지막 접속 시간을 기억해야 한다면, 이 정보가 상태로 관리됩니다. 이 상태 정보는 주기적으로 스냅샷을 찍어두어, 시스템에 장애가 발생했다가 복구되어도 이전 상태를 그대로 복원하여 중단 없이 계산을 이어갈 수 있게 합니다(Fault Tolerance).

3.  **데이터 제공/저장 (Serving/Storage):**
    -   Flink에서 처리된 결과는 최종 목적지인 **싱크**로 전달됩니다.
    -   실시간 대시보드에 보여주기 위해 **Elasticsearch**나 **Apache Druid** 같은 실시간 분석에 특화된 데이터베이스로 보낼 수 있습니다.
    -   다른 시스템에 특정 행동을 촉발시키기 위해 다시 **Kafka**의 다른 토픽으로 이벤트를 보낼 수도 있습니다 (예: '부정사용 의심' 이벤트 발행).
    -   장기 보관 및 분석을 위해 **데이터 레이크**(예: AWS S3)나 **데이터 웨어하우스**(예: Snowflake)에 저장할 수도 있습니다.

이 세 단계가 파이프라인처럼 연결되어 데이터가 발생하는 순간부터 가치를 창출하는 순간까지 멈춤 없이 흐르게 됩니다.

### 4. 등장·부상 시점 (2022~2026 중 어느 해에 왜 떴는지, 연도별 흐름)

-   **~2021 (태동기 및 성장기):** 실시간 데이터 플랫폼의 핵심 기술인 Apache Kafka(2011년), Spark Streaming(2013년), Apache Flink(2014년) 등은 이미 2010년대에 등장했습니다. 이 시기에는 주로 기술적 성숙도가 높은 빅테크 기업(LinkedIn, Netflix, Uber 등)들이 자체적으로 복잡한 플랫폼을 구축하여 사용하는 '전문가의 시대'였습니다.

-   **2022~2023 (주류 기술로 부상):** 이 시기부터 실시간 데이터 플랫폼은 더 이상 일부 빅테크의 전유물이 아니게 됩니다.
    -   **이유 1 (클라우드 기반 관리형 서비스의 대중화):** AWS의 Kinesis, Google Cloud의 Dataflow, 그리고 Kafka의 창시자들이 만든 **Confluent**의 'Confluent Cloud'와 같은 완전 관리형 서비스가 등장했습니다. 이로 인해 기업들은 복잡한 인프라 운영 부담 없이, 월 사용료만 내고 손쉽게 실시간 데이터 플랫폼을 도입할 수 있게 되었습니다.
    -   **이유 2 (데이터 통합의 필요성 증대):** 기업 내에 흩어져 있는 수많은 마이크로서비스와 SaaS(Salesforce, Google Analytics 등) 데이터를 실시간으로 통합하여 비즈니스 현황을 파악하려는 요구가 폭발적으로 증가했습니다.
    -   **대표 사례:** 이 시기에 많은 이커머스 기업들이 실시간 재고 관리 및 개인화 추천 시스템을 도입했고, 핀테크 기업들은 FDS(부정거래탐지시스템)를 고도화했습니다.

-   **2024~2026 (성숙기 및 지능화):** 현재와 가까운 미래입니다.
    -   **트렌드 1 (실시간 AI/ML):** 플랫폼 위에서 단순 집계를 넘어, 실시간으로 들어오는 데이터를 가지고 AI/ML 모델을 학습시키거나, 추론하는 '실시간 머신러닝'이 핵심 트렌드로 자리 잡고 있습니다. 예를 들어, 유튜브는 사용자가 지금 보고 있는 영상과 상호작용하는 패턴을 실시간으로 분석하여 다음에 추천할 영상을 즉시 결정합니다.
    -   **트렌드 2 (플랫폼의 플랫폼화):** Confluent와 같은 기업들은 단순히 Kafka를 제공하는 것을 넘어, 데이터 처리(Flink), 거버넌스, 보안 기능을 모두 통합한 '데이터 스트리밍 플랫폼'을 제공하며 시장을 주도하고 있습니다. (참고: Confluent의 2023년, 2024년 연례 보고서 'State of Data in Motion')
    -   **트렌드 3 (간편화 및 대중화):** SQL만으로 스트림 데이터를 처리할 수 있는 `ksqlDB`(Confluent), `Flink SQL` 등이 더욱 발전하여, 데이터 분석가나 백엔드 개발자들도 쉽게 실시간 분석에 참여할 수 있게 될 것입니다. (추정) 2026년경에는 많은 기업들이 주요 데이터 파이프라인의 상당 부분을 실시간으로 전환할 것으로 예상됩니다.

### 5. 장점 (근거: 대표 사례·제품·기업·보고서명 명시)

1.  **즉각적인 비즈니스 통찰력과 의사결정 지원:**
    -   **근거:** 넷플릭스(Netflix)는 Apache Flink를 사용하여 사용자의 시청 기록, 클릭, 검색 등 모든 상호작용을 실시간으로 처리하여 개인화된 콘텐츠 추천 목록을 수 분 내에 업데이트합니다. 이는 '하루에 한 번' 추천 목록을 업데이트하는 것과 비교할 수 없는 사용자 경험을 제공합니다. (출처: Netflix Technology Blog)

2.  **프로액티브한 위기 대응 및 기회 포착:**
    -   **근거:** 글로벌 결제 기업 **Stripe**은 스트림 처리 기술을 활용하여 초당 수천 건의 결제를 실시간으로 분석하고, 사기성 거래 패턴을 즉시 탐지하여 승인을 거절합니다. 이를 통해 연간 수억 달러의 사기 피해를 예방합니다. (출처: Stripe Engineering Blog)

3.  **향상된 사용자 경험과 만족도:**
    -   **근거:** **우버(Uber)**는 Kafka와 Flink를 기반으로 한 실시간 플랫폼을 통해 운전자와 탑승객의 위치를 수 초 간격으로 업데이트하고, 예상 도착 시간(ETA)을 정확하게 계산하며, 요금을 실시간으로 배정합니다. 이는 서비스의 신뢰도와 직결됩니다. (출처: Uber Engineering Blog)

4.  **효율적인 시스템 아키텍처 구축:**
    -   **근거:** **아디다스(Adidas)**는 기존의 복잡한 점대점(Point-to-Point) 데이터 연동 방식을 버리고, Confluent Cloud를 중앙 허브로 하는 이벤트 기반 아키텍처(Event-Driven Architecture)로 전환했습니다. 이를 통해 시스템 간의 결합도를 낮추고, 신규 서비스 개발 속도를 3~4배 향상시켰습니다. (출처: Confluent 공식 홈페이지 고객 사례)

### 6. 단점·비용·리스크 (근거 명시)

1.  **높은 기술적 복잡성과 운영 부담:**
    -   **근거:** 자체적으로 Kafka, Flink 클러스터를 구축하고 운영하는 것은 매우 어렵습니다. 각 컴포넌트의 버전을 맞추고, 성능을 튜닝하며, 24시간 장애를 감시하는 데는 숙련된 데이터 엔지니어 팀이 필요합니다. **월마트(Walmart)**와 같은 거대 기업조차도 초기에는 자체 구축으로 어려움을 겪다가, 나중에는 전문 솔루션과 클라우드 서비스를 적극 활용하는 방향으로 전환했습니다. (근거: 여러 기술 컨퍼런스 발표 자료)

2.  **높은 초기 도입 비용 및 인력 비용:**
    -   **근거:** Confluent Cloud나 AWS Kinesis와 같은 관리형 서비스는 운영 부담을 줄여주지만, 사용한 만큼 비용을 내는 구조이므로 데이터 처리량이 많아지면 월 수천만 원 이상의 비용이 발생할 수 있습니다. 또한, Gartner 보고서에 따르면 실시간 데이터 처리 기술을 다룰 수 있는 전문 인력(Data Engineer, Streaming Architect)의 몸값이 매우 높아, 인재 확보 경쟁이 치열하고 높은 연봉을 지불해야 합니다.

3.  **데이터 처리의 정확성 보장 문제:**
    -   **근거:** 스트림 처리에서는 '정확히 한 번 처리(Exactly-once Semantics)'를 보장하는 것이 매우 어렵습니다. 네트워크 문제로 데이터가 중복 전송되어 두 번 처리되거나(At-least-once), 장애로 인해 유실(At-most-once)될 수 있습니다. **Apache Flink**는 2단계 커밋 프로토콜을 통해 이를 해결하는 정교한 메커니즘을 제공하지만, 이 기능을 활성화하면 성능이 저하될 수 있고, 모든 소스와 싱크가 이 프로토콜을 지원해야 한다는 제약이 있습니다.

### 7. 한계점·미해결 난제 (기술적/윤리적/규제)

1.  **기술적 한계 - 거대한 상태(State) 관리의 어려움:**
    -   Stateful 스트림 처리에서, 분석 기간이 길어지거나 추적해야 할 대상이 많아지면 '상태'의 크기가 수 테라바이트(TB)까지 커질 수 있습니다. Flink가 사용하는 **RocksDB** 같은 기술로 로컬 디스크에 상태를 저장할 수 있지만, 상태가 너무 커지면 백업과 복구에 몇 시간이 걸리게 되어 '실시간'이라는 의미가 퇴색됩니다. 이는 현재 스트림 처리 엔진들이 마주한 가장 큰 기술적 난제 중 하나입니다.

2.  **기술적 한계 - '진정한' 실시간의 물리적 제약:**
    -   데이터가 생성되어 처리되고 결과가 나오기까지의 시간(End-to-end Latency)을 '0'으로 만드는 것은 불가능합니다. 네트워크 지연, 처리 로직의 복잡도, 데이터 직렬화/역직렬화 시간 등 모든 단계에서 미세한 지연이 누적됩니다. 특히 전 지구적으로 분산된 서비스에서는 빛의 속도라는 물리적 한계 때문에 수십~수백 밀리초(ms)의 지연은 필연적입니다.

3.  **규제/윤리적 문제 - 데이터 프라이버시 및 삭제 요청 처리:**
    -   GDPR(유럽 개인정보보호법)과 같은 규제는 사용자가 자신의 데이터 삭제를 요청할 권리를 보장합니다. 하지만 끊임없이 흐르고, 집계되고, 변형되는 데이터 스트림 속에서 특정 사용자의 데이터 조각들만 정확히 찾아내어 삭제하는 것은 매우 어렵습니다. 특히, 한 번 집계된 결과(예: '오늘의 시간대별 평균 사용자 수')에 포함된 개인의 흔적을 되돌리는 것은 거의 불가능에 가깝습니다. 이는 실시간 데이터 플랫폼 설계 시 반드시 고려해야 할 규제 준수 문제입니다.

### 8. 필요한 수학적·이론적 개념

실시간 데이터 플랫폼을 깊이 이해하기 위해서는 몇 가지 이론적 배경이 도움이 됩니다.

-   **람다 아키텍처 (Lambda Architecture) vs 카파 아키텍처 (Kappa Architecture):**
    -   전통적으로 실시간 데이터 플랫폼은 '람다 아키텍처'를 따랐습니다. 이는 실시간 처리를 위한 '스피드 레이어'와, 배치 처리를 통해 데이터의 정합성을 보정하는 '배치 레이어'를 둘 다 운영하는 복잡한 구조입니다.
    -   최근에는 스트림 처리 엔진의 성능과 안정성이 향상되면서, 모든 처리를 스트림으로만 해결하려는 '카파 아키텍처'가 대세가 되고 있습니다. 이는 구조를 단순화하고 운영 비용을 절감하는 효과가 있습니다.

-   **확률적 자료구조 (Probabilistic Data Structures):**
    -   수십억 건의 스트림 데이터에서 '정확한' 값을 계산하는 것은 매우 비효율적일 수 있습니다. 이때 약간의 오차를 허용하는 대신, 훨씬 적은 메모리와 계산량으로 '근사치'를 빠르게 얻는 자료구조를 사용합니다.
    -   **HyperLogLog:** 매우 적은 메모리(수 KB)로 스트림에 포함된 유니크한 아이템의 개수(Cardinality)를 추정할 수 있습니다. (예: 오늘 하루 동안 우리 웹사이트를 방문한 순 방문자 수 추정)
    -   **Bloom Filter:** 특정 아이템이 집합에 속해있는지를 매우 빠르게 검사할 수 있습니다. '없다'고 하면 100% 확실하지만, '있다'고 하면 아주 낮은 확률로 틀릴 수 있습니다. (예: 이미 처리한 이벤트인지 중복 체크할 때 사용)

-   **시간 개념 (Time Semantics):**
    -   **이벤트 시간 (Event Time):** 이벤트가 실제로 발생한 시간. 가장 정확하지만, 네트워크 지연 등으로 뒤늦게 도착할 수 있습니다.
    -   **처리 시간 (Processing Time):** 스트림 처리 엔진이 이벤트를 처리하는 시간. 가장 간단하지만, 처리 시점의 부하에 따라 결과가 달라져 일관성을 보장하기 어렵습니다.
    -   정확한 분석을 위해서는 '이벤트 시간'을 기준으로 처리해야 하며, 이때 '워터마크' 개념이 필수적으로 사용됩니다.

### 9. PT 발표 주제화

#### 주제 후보 1: **컨테이너 환경의 실시간 이상 행위 탐지, Flink로 구현하기**

-   **한 줄 메시지:** 리눅스 커널 수준에서 수집한 시스템 콜 스트림을 실시간 데이터 플랫폼으로 분석하여, 기존 보안 솔루션이 놓치는 컨테이너 이상 행위를 즉시 탐지하는 방법을 제안합니다.
-   **개요:**
    -   **서론:** 컨테이너 환경의 보안 위협 증가와 기존 정적 분석의 한계를 지적. 실시간 행위 분석의 필요성 제기.
    -   **본론:**
        1.  eBPF와 같은 커널 기술을 이용해 컨테이너의 시스템 콜을 실시간 스트림으로 수집하는 방법 설명 (데이터 소스).
        2.  수집된 데이터를 Kafka로 안정적으로 전송하고, Flink를 이용해 처리하는 아키텍처 제시.
        3.  Flink의 상태 저장 기능을 활용하여 각 컨테이너의 '정상 행위 프로필'(예: 평소 호출하는 시스템 콜 목록, 파일 접근 패턴)을 학습하고 상태로 저장.
        4.  새로운 시스템 콜 이벤트가 들어올 때마다 저장된 프로필과 비교하여, 비정상적인 패턴(예: 갑자기 네트워크 소켓을 열거나, 민감한 파일에 접근)을 탐지하는 로직 시연.
    -   **결론:** 제안 시스템의 기대효과(탐지 시간 단축, 제로데이 공격 대응 가능성)와, SSAFY에서 배울 풀스택 기술을 통해 이 시스템을 실제 웹 기반 관제 대시보드로 구현해보고 싶다는 포부로 마무리.
-   **예상 꼬리질문:**
    1.  **Q:** 시스템 콜 데이터는 양이 엄청날 텐데, Kafka와 Flink가 그 부하를 감당할 수 있을까요? 성능상 고려할 점은 무엇인가요?
        **A:** 좋은 질문입니다. 물론 모든 시스템 콜을 그대로 보내는 것은 비효율적일 수 있습니다. 1차적으로 커널단(eBPF)에서 의미 있는 이벤트만 필터링하거나 사전 집계하여 데이터 양을 줄이는 것이 중요합니다. 또한 Kafka에서는 토픽의 파티션 수를 늘려 병렬 처리를 극대화하고, Flink에서는 데이터의 Key를 컨테이너 ID 등으로 적절히 분산시켜 특정 노드에 부하가 몰리지 않도록 하는 '키 그룹핑(Key Grouping)' 전략이 필요합니다.
    2.  **Q:** '정상 행위 프로필'을 만드는 기준이 모호할 수 있습니다. 애플리케이션이 업데이트되면 정상 패턴도 바뀌는데, 어떻게 대응해야 할까요?
        **A:** 핵심적인 질문입니다. 그래서 '정적 룰 기반'이 아닌 '동적 학습'이 필요합니다. Flink 잡을 통해 지속적으로 정상 패턴을 재학습하고, 특정 기간 동안의 패턴 변화를 감지하여 프로필을 자동으로 업데이트하는 MLOps 파이프라인을 구축해야 합니다. 또한, 새로운 배포가 시작될 때 '학습 모드'를 활성화하여 일정 시간 동안은 경고를 보내지 않고 새로운 패턴을 학습하게 하는 운영적 기법도 병행해야 합니다.
    3.  **Q:** Flink 대신 Spark Streaming을 사용할 수도 있었을 텐데, Flink를 선택한 특별한 이유가 있나요?
        **A:** Spark Streaming은 마이크로 배치(Micro-batch) 방식으로 동작하여 짧은 시간의 데이터를 묶어 처리하는 반면, Flink는 한 번에 하나씩 진정한 이벤트 단위 스트림 처리가 가능하여 더 낮은 지연 시간(Latency)을 제공합니다. 보안 이벤트는 1초의 지연도 치명적일 수 있으므로, ms 단위의 빠른 응답이 가능한 Flink가 더 적합하다고 판단했습니다. 또한, Flink의 정교한 상태 관리와 이벤트 시간 처리 기능은 이상 행위 탐지와 같은 복잡한 로직 구현에 더 유리합니다.

#### 주제 후보 2: **실시간 데이터 플랫폼을 활용한 차세대 개발자 협업 도구의 재해석**

### 10. 지원자 경험 연결 각도 (컨테이너 보안·커널·syscall 이상탐지·인프라 관점에서 엮는 법)

면접관님, 저의 가장 큰 강점은 시스템의 가장 낮은 곳, 즉 리눅스 커널과 컨테이너의 동작 원리를 이해하고 있다는 점입니다. 저는 이 강점을 실시간 데이터 플랫폼이라는 거대한 흐름과 연결하여 시너지를 내고 싶습니다.

제가 수행했던 '시스템 콜 동적 관측을 통한 이상탐지' 프로젝트는 사실상 '소규모 실시간 데이터 플랫폼'의 원리와 맞닿아 있습니다.
-   **데이터 소스:** 컨테이너에서 발생하는 수많은 **시스템 콜**이 바로 실시간 **이벤트 스트림**입니다.
-   **처리 로직:** 제가 만들었던 '정상 행위 프로필'과 비교하여 이상 여부를 판단하는 로직은, Flink의 **상태 저장 처리(Stateful Processing)**와 정확히 일치하는 개념입니다. 저는 특정 컨테이너의 과거 행적을 '상태'로 기억하고, 새로운 행위가 이 상태와 일치하는지 검사하는 로직을 구현했던 것입니다.
-   **인프라 관점:** 저는 이 경험을 통해, 단순히 알고리즘을 만드는 것을 넘어 대량의 데이터를 어떻게 효율적으로 수집하고(eBPF), 어떻게 지연 없이 처리하며, 어떻게 안정적으로 시스템을 유지할 것인가 하는 **인프라와 아키텍처의 중요성**을 깨달았습니다.

저는 저의 경험을 발표 주제로 삼아, "컨테이너에서 발생하는 raw한 시스템 콜 스트림을 Kafka와 Flink를 이용한 대규모 실시간 데이터 플랫폼 위에서 분석하여, 수만 개의 컨테이너를 동시에 감시하고 이상 징후를 1초 안에 탐지하는 시스템을 구축하는 방법"을 제안하고 싶습니다.

이는 저의 '커널 수준의 깊이'와 SSAFY에서 배우고 싶은 '애플리케이션 및 시스템 아키텍처' 역량을 결합하여 '융합형 개발자'로 성장하고 싶다는 저의 비전을 가장 잘 보여주는 주제라고 생각합니다. 저의 로우레벨 시스템 경험은, 실시간 데이터 플랫폼을 구축할 때 발생할 수 있는 까다로운 성능 문제나 네트워크 문제를 해결하는 데 있어 남들과 다른 깊이 있는 해결책을 제시할 수 있는 튼튼한 기반이 될 것입니다.

### 11. PT 적합도 평가

-   **난이도: 상**
    -   **이유:** 다루는 기술(Kafka, Flink, eBPF) 각각의 깊이가 상당하고, 이들을 조합한 아키텍처는 현업에서도 높은 수준의 전문성을 요구합니다. 개념을 정확히 이해하고 설명하지 못하면 바로 밑천이 드러날 수 있습니다.

-   **면접관 흥미도: 상**
