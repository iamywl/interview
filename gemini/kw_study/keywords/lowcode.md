## 로우코드/노코드 (lowcode)
### 1. 한 줄 정의와 큰 그림 (무엇을 푸는 기술/이슈인가, 왜 중요한가)
로우코드/노코드는 코딩을 최소화하거나 전혀 하지 않고도 GUI(그래픽 사용자 인터페이스)를 통해 애플리케이션을 개발하는 접근 방식이며, 개발자 부족 문제와 비즈니스 부서의 신속한 앱 개발 요구를 해결하기 위해 중요합니다.

### 2. 핵심 개념·용어 정의 (하향식, 충분히 많이)
*   **로우코드 (Low-Code):** 최소한의 코딩으로 애플리케이션을 개발하는 플랫폼. 시각적인 개발 환경과 사전 빌드된 컴포넌트를 제공하지만, 필요시 개발자가 직접 코드를 작성하여 기능을 확장하거나 세부 조정을 할 수 있습니다.
*   **노코드 (No-Code):** 코딩 없이 순수하게 GUI 환경에서 드래그앤드롭(Drag-and-Drop) 방식으로만 애플리케이션을 만드는 플랫폼. 주로 비개발 직군(시민 개발자)이 간단한 비즈니스 로직을 자동화하거나 단순한 앱을 만들 때 사용합니다.
*   **시민 개발자 (Citizen Developer):** IT 부서 소속이 아닌 현업 부서 직원으로서, IT 부서의 승인 하에 로우코드/노코드 플랫폼을 사용하여 비즈니스 애플리케이션을 직접 개발하는 사람.
*   **GUI (Graphical User Interface):** 사용자가 그래픽(아이콘, 메뉴 등)을 통해 컴퓨터와 상호작용하는 방식. 로우코드/노코드 플랫폼은 GUI를 통해 개발 과정을 시각화합니다.
*   **Visual Development:** 코드 대신 시각적인 모델과 인터페이스를 사용하여 소프트웨어를 개발하는 방식. 로우코드/노코드의 핵심적인 특징입니다.
*   **Drag-and-Drop:** 화면 상의 그래픽 객체를 마우스로 끌어다 놓는 동작으로, 로우코드/노코드 플랫폼에서 UI(사용자 인터페이스)를 구성하거나 기능 흐름을 정의할 때 사용됩니다.
*   **Model-Driven Development (MDD):** 소프트웨어의 기능과 로직을 추상적인 '모델'로 정의하면, 플랫폼이 이 모델을 해석하여 실제 작동하는 코드를 자동으로 생성하는 개발 방식. 로우코드의 근간이 되는 기술입니다.
*   **컴포넌트 (Component):** 재사용 가능한 소프트웨어 부품. 로우코드 플랫폼은 로그인, 데이터 그리드, 차트 등 미리 만들어진 다양한 컴포f넌트를 제공하여 개발 생산성을 높입니다.
*   **API (Application Programming Interface):** 애플리케이션 간에 데이터를 주고받고 기능을 호출하기 위한 약속(규칙). 로우코드/노코드 플랫폼은 외부 서비스(결제, 지도, 소셜 로그인 등)와 연동하기 위해 API 통합 기능을 제공합니다.
*   **PaaS (Platform as a Service):** 애플리케이션을 개발하고 실행하는 데 필요한 모든 환경(인프라, OS, 미들웨어 등)을 클라우드 서비스 형태로 제공하는 모델. 대부분의 로우코드/노코드 플랫폼은 PaaS 형태로 제공되어 사용자가 인프라 관리에 신경 쓸 필요가 없습니다.

### 3. 동작 원리·구조 (단계별로 자세히)
1.  **추상화 (Abstraction) 단계:** 개발자가 GUI를 통해 원하는 기능과 데이터 구조, 비즈니스 로직을 시각적인 모델(예: 순서도, 다이어그램, 폼)로 정의합니다. 이 모델은 특정 프로그래밍 언어나 기술에 종속되지 않은, 매우 높은 수준의 추상화된 설계도입니다.
2.  **메타데이터 변환 (Metadata Conversion) 단계:** 플랫폼은 사용자가 생성한 시각적 모델을 내부적으로 이해할 수 있는 구조화된 데이터, 즉 '메타데이터'로 변환합니다. 이 메타데이터에는 UI 구성, 데이터 스키마, 워크플로우 규칙 등 애플리케이션에 대한 모든 정보가 담겨있습니다.
3.  **코드 생성 (Code Generation) 단계:** 플랫폼의 '엔진'이 이 메타데이터를 해석하여 실제 실행 가능한 코드를 자동으로 생성합니다. 생성되는 코드는 플랫폼에 따라 Java, C#, JavaScript 등 다양하며, 웹/모바일 등 목표 환경에 맞는 코드를 만들어냅니다. 노코드 플랫폼은 이 과정이 완전히 숨겨져 있고, 로우코드 플랫폼은 생성된 코드의 일부를 개발자가 수정할 수 있도록 허용하기도 합니다.
4.  **컴파일 및 배포 (Compile & Deploy) 단계:** 생성된 소스 코드는 일반적인 개발 과정과 마찬가지로 컴파일, 빌드 과정을 거쳐 실행 가능한 애플리케이션으로 만들어집니다. 이후 내장된 배포 시스템을 통해 버튼 클릭 몇 번으로 클라우드 서버나 특정 환경에 애플리케이션을 배포하고 실행합니다.
5.  **실행 및 운영 (Runtime & Operation) 단계:** 배포된 애플리케이션은 런타임 환경에서 실행됩니다. 이 때 플랫폼은 사용자 인증, 데이터베이스 연결, API 호출, 서버 자원 할당 등 애플리케이션 실행에 필요한 모든 것을 관리하고 모니터링합니다.

### 4. 등장·부상 시점 (2022~2026 중 어느 해에 왜 떴는지, 연도별 흐름)
*   **2022년 이전:** 개념 자체는 오래전부터 존재했지만, 주로 기업 내 특정 업무 자동화(BPM, Business Process Management)나 간단한 웹사이트 빌더 수준에 머물렀습니다.
*   **2022~2023년:** COVID-19 팬데믹으로 비대면 업무와 디지털 전환(DX)이 가속화되면서 폭발적으로 부상했습니다. 기업들은 급변하는 비즈니스 환경에 빠르게 대응하기 위해 애플리케이션을 신속하게 개발하고 배포해야 했고, 동시에 개발자 부족 현상은 심화되었습니다. 이 두 가지 문제가 맞물리면서 로우코드/노코드가 현실적인 대안으로 주목받기 시작했습니다. 가트너(Gartner)와 같은 시장조사기관이 이 시기부터 로우코드를 핵심 전략 기술로 꾸준히 언급하며 시장의 기대감을 높였습니다.
*   **2024년 (현재):** 생성형 AI(Generative AI)와 결합이 핵심 트렌드로 자리 잡았습니다. 단순히 드래그앤드롭하는 것을 넘어, 자연어로 "고객 관리용 앱을 만들어줘"라고 입력하면 AI가 기본적인 앱 구조와 화면, 로직을 자동으로 생성해주는 수준으로 발전하고 있습니다. 마이크로소프트의 'Power Apps'는 코파일럿(Copilot)을 통해, 세일즈포스(Salesforce)는 '아인슈타인(Einstein) 1 플랫폼'을 통해 AI 기반 로우코드 개발을 지원하는 것이 대표적입니다.
*   **2025~2026년 (전망):** 전문 개발자와 시민 개발자 간의 협업이 더욱 중요해지고, 엔터프라이즈급의 복잡하고 미션 크리티컬한 애플리케이션 개발 영역으로 점차 확장될 것으로 보입니다. 또한, 생성되는 코드의 품질과 보안, 거버넌스(Governance)를 체계적으로 관리하는 기술이 핵심 경쟁력이 될 것입니다. (추정)

### 5. 장점 (근거: 대표 사례·제품·기업·보고서명 명시)
*   **개발 속도 및 생산성 향상:** 전통적인 개발 방식 대비 앱 개발 기간을 획기적으로 단축합니다. **근거:** Forrester 보고서 "The Total Economic Impact™ Of The Appian Low-Code Platform"에 따르면, Appian 플랫폼을 사용한 기업들은 애플리케이션 개발 속도가 10배 빨라졌다고 보고했습니다.
*   **개발 비용 절감:** 전문 개발자 채용 및 유지에 드는 비용과 시간을 줄일 수 있습니다. **근거:** OutSystems는 자사 플랫폼을 도입한 한 금융사가 3년 동안 1,000만 달러 이상의 IT 비용을 절감했다고 사례를 발표했습니다. (OutSystems 웹사이트 성공 사례)
*   **비즈니스 민첩성 증가:** 시장 변화나 고객 요구에 신속하게 대응하는 애플리케이션을 빠르게 출시할 수 있습니다. **근거:** 코로나19 초기에 많은 기업들이 Mendix 플랫폼을 사용하여 백신 접종 예약 시스템, 재택근무 관리 앱 등을 몇 주 만에 개발하여 배포했습니다. (Mendix COVID-19 Response 사례)
*   **IT-현업 간 협업 강화:** 시각적인 개발 환경을 통해 비개발자인 현업 담당자가 개발 과정에 직접 참여하고 피드백을 줄 수 있어, 요구사항 불일치로 인한 재작업을 줄입니다. **근거:** 마이크로소프트 Power Platform은 현업(마케팅, 재무 등)과 IT 부서가 함께 앱을 만들고 데이터를 분석하는 'Fusion Development' 모델을 강조하며 성공 사례를 다수 보유하고 있습니다.
*   **IT 인력난 해소:** 모든 개발을 전문 개발자에게 의존하지 않고, 단순하고 반복적인 작업은 시민 개발자에게 위임하여 전문 개발자가 더 높은 가치를 창출하는 복잡한 문제에 집중하도록 합니다. **근거:** ServiceNow는 자사 로우코드 플랫폼(Now Platform)을 통해 기업들이 IT 서비스 요청의 상당 부분을 자동화하고, 시민 개발자들이 직접 간단한 워크플로우를 구성하여 IT 부서의 업무 부담을 줄인 사례를 제시합니다.

### 6. 단점·비용·리스크 (근거 명시)
*   **플랫폼 종속성 (Vendor Lock-in):** 특정 로우코드 플랫폼으로 개발한 앱은 다른 환경으로 이전하거나 해당 플랫폼 없이 유지보수하기 매우 어렵습니다. **근거:** 대부분의 로우코드 플랫폼(예: Salesforce, ServiceNow)은 자사 생태계 내에서만 최적의 성능을 발휘하도록 설계되어 있어, 한번 도입하면 다른 플랫폼으로 전환하는 데 막대한 비용과 시간이 듭니다.
*   **제한된 확장성과 커스터마이징:** 플랫폼이 제공하는 기능과 컴포넌트의 한계를 벗어나는 복잡한 로직이나 독창적인 UI/UX를 구현하기 어렵습니다. **근거:** 노코드 툴인 Bubble이나 Adalo로 만든 앱들은 특정 플러그인이 지원하지 않는 독특한 API 연동이나, 하드웨어 직접 제어와 같은 기능을 구현하는 데 명백한 한계가 있습니다.
*   **숨겨진 비용 (Hidden Costs):** 초기 개발 비용은 낮을 수 있으나, 사용자 수, 데이터 처리량, API 호출 횟수에 따라 라이선스 비용이 기하급수적으로 증가할 수 있습니다. **근거:** 많은 로우코드 플랫폼의 가격 정책은 '사용량 기반 과금(Usage-based Pricing)' 모델을 따릅니다. 예를 들어, OutSystems나 Mendix의 엔터프라이즈 요금제는 앱의 규모와 사용자 수가 늘어날수록 상당한 비용이 발생할 수 있습니다.
*   **보안 및 거버넌스 문제 (Shadow IT):** 현업 부서에서 IT 부서의 통제 없이 무분별하게 앱을 개발하고 사용하는 '섀도우 IT(Shadow IT)' 현상을 야기할 수 있습니다. 이는 데이터 유출, 보안 취약점, 규정 준수 문제로 이어질 수 있습니다. **근거:** 가트너는 "Low-Code-First" 전략을 채택하는 기업의 가장 큰 과제 중 하나로 거버넌스 부재를 꼽으며, 이를 해결하기 위한 'Center of Excellence(전문가 조직)' 구성을 권고합니다.
*   **성능 문제:** 복잡한 데이터 처리나 대규모 트랜잭션을 처리할 때, 직접 작성한 최적화된 코드에 비해 성능이 저하될 수 있습니다. **근거:** 로우코드 플랫폼이 생성하는 코드는 범용성을 위해 최적화되지 않은 경우가 많아, 대규모 사용자가 동시에 접속하는 서비스(예: 이커머스 실시간 경매)에는 부적합할 수 있다는 기술 블로그 및 커뮤니티의 지적이 많습니다.

### 7. 한계점·미해결 난제 (기술적/윤리적/규제)
*   **기술적 한계:**
    *   **고성능/실시간 처리:** 게임, 고빈도 거래 시스템(HFT), 실시간 영상 처리 등 극도의 성능과 낮은 지연 시간(low latency)이 요구되는 애플리케이션 개발에는 부적합합니다.
    *   **레거시 시스템 통합:** 오래된 메인프레임이나 특수한 프로토콜을 사용하는 사내 시스템과의 통합은 여전히 복잡하고 많은 수작업을 요구합니다.
    *   **코드 품질 및 디버깅:** 자동으로 생성된 코드의 품질이 항상 보장되지 않으며, 복잡한 문제 발생 시 내부 동작을 알 수 없어 디버깅이 매우 어렵습니다. "블랙박스"처럼 동작하는 경우가 많습니다.
*   **윤리적/규제적 한계:**
    *   **책임 소재의 모호함:** 로우코드 플랫폼을 이용해 만든 앱에서 데이터 유출이나 금전적 사고가 발생했을 때, 그 책임이 앱을 만든 시민 개발자에게 있는지, 플랫폼 제공 업체에 있는지, 아니면 거버넌스 정책을 수립한 기업에 있는지 불분명합니다.
    *   **데이터 프라이버시:** GDPR, CCPA 등 강화되는 개인정보보호 규제를 로우코드 플랫폼이 생성한 앱이 모두 완벽하게 준수하는지 검증하기 어렵습니다. 특히 데이터가 어느 지역의 서버에 저장되고 처리되는지 명확히 통제하기 어려울 수 있습니다.
    *   **개발자 역할의 축소 및 윤리:** 로우코드가 확산되면서 주니어 개발자의 일자리가 줄어들 수 있다는 우려와 함께, 개발자의 전문성을 '코드'가 아닌 '비즈니스 문제 해결'로 재정의해야 한다는 윤리적 고민이 대두됩니다.

### 8. 필요한 수학적·이론적 개념
로우코드/노코드 자체는 직접적인 수학이나 복잡한 이론을 사용자에게 요구하지 않는 것이 핵심입니다. 하지만 그 내부 동작 원리는 다음과 같은 컴퓨터 과학의 근간이 되는 개념들에 기반합니다.
*   **추상화 (Abstraction):** 복잡한 시스템을 단순한 모델로 표현하는 핵심 원리. 로우코드 플랫폼은 코드, 인프라, 데이터베이스 등 복잡한 기술 스택을 GUI라는 단순한 모델로 추상화하여 제공합니다.
*   **오토마타 이론 (Automata Theory):** 상태(State)와 전이(Transition)를 통해 시스템의 동작을 정의하는 이론. 로우코드의 워크플로우나 비즈니스 프로세스 모델링(BPMN)은 유한 상태 기계(Finite State Machine) 개념에 깊이 뿌리를 두고 있습니다. "결재 요청" 상태에서 "승인" 또는 "반려" 입력에 따라 "결재 완료" 또는 "재작성" 상태로 전이하는 로직이 대표적인 예입니다.
*   **그래프 이론 (Graph Theory):** 노드(Node)와 엣지(Edge)로 관계를 표현하는 이론. 로우코드의 시각적 개발 환경에서 UI 요소들의 관계, 데이터 모델의 관계, 워크플로우의 흐름 등은 모두 그래프 형태로 표현되고 처리됩니다.
*   **복잡도 이론 (Complexity Theory):** 로우코드 플랫폼이 생성하는 코드의 효율성을 분석할 때 O-표기법(Big O notation)과 같은 개념이 내부적으로 중요합니다. 예를 들어, 플랫폼이 비효율적인 O(n²) 알고리즘으로 코드를 생성한다면 데이터가 많아질수록 성능이 급격히 저하될 것입니다. 사용자가 직접 코드를 수정할 수 없는 노코드의 경우 이는 치명적인 한계가 됩니다.

### 9. PT 발표 주제화
#### 주제 후보
1.  **AI 융합 시대, 로우코드/노코드는 개발자의 위협인가 기회인가?**
2.  **섀도우 IT의 역습: 로우코드 확산에 따른 보안 위협과 인프라 관점의 해결 방안**
3.  **시민 개발자, 과연 만능일까? 로우코드 플랫폼의 기술적 한계와 미래**

#### 발표 개요 (주제 2번 예시)
*   **한 줄 메시지:** "로우코드는 개발 생산성을 높이는 강력한 도구이지만, 통제되지 않으면 컨테이너 환경의 보안 구멍처럼 심각한 '섀도우 IT' 위협이 될 수 있습니다. 저는 인프라 레벨의 관측과 통제를 통해 이 문제를 해결할 수 있다고 생각합니다."
*   **서론 (문제 제기):**
    *   개발자 부족, 빠른 비즈니스 요구... 로우코드가 왜 지금 주목받는가?
    *   하지만 동전의 양면처럼, 현업 부서의 무분별한 앱 개발(섀도우 IT)이라는 그림자가 커지고 있음.
    *   이는 마치 권한 관리 없는 루트 계정 공유와 같이 위험한 상황.
*   **본론 (심층 분석 및 해결 방안):**
    *   **위협 1: 데이터 유출:** 통제되지 않은 API 연동, 민감 데이터의 부적절한 처리 문제. (사례 제시)
    *   **위협 2: 보안 취약점:** 플랫폼 자체의 취약점, 또는 시민 개발자의 미숙한 설계로 인한 로직 오류.
    *   **해결 방안(나의 관점):** 이 문제를 애플리케이션 레벨에서만 막는 것은 한계. 인프라 레벨의 접근이 필요함.
        *   **1) 관측(Observability):** 로우코드 앱들이 어떤 API를 호출하고, 어떤 서버와 통신하며, 어떤 시스템 콜을 발생시키는지 중앙에서 모니터링하는 '관제탑' 구축.
        *   **2) 통제(Control):** 컨테이너 보안에서 기준 행위(baseline)를 정의하고 이상 행위를 탐지하듯, 허가된 API 호출 목록(Allowlist), 비정상적인 데이터 접근 패턴 등을 정의하고 정책 기반으로 자동 차단(Enforcement).
*   **결론 (기여 방안):**
    *   로우코드는 거스를 수 없는 흐름. 중요한 것은 '어떻게 관리하고 통제하며 사용할 것인가'의 문제.
    *   저는 리눅스 커널과 시스템 콜을 분석했던 경험을 살려, 로우코드 플랫폼이 생성하는 '블랙박스' 같은 애플리케이션의 내부 동작을 인프라 관점에서 투명하게 들여다보고 통제하는 기술에 기여하고 싶음.
    *   SSAFY에서 풀스택 개발 역량을 익혀, 단순히 앱을 만드는 것을 넘어 안전한 로우코드 개발 생태계를 구축하는 융합형 개발자로 성장하겠음.

#### 예상 꼬리질문 및 답변 방향
1.  **질문:** 로우코드 플랫폼은 보통 PaaS 형태로 제공되어 인프라 접근이 제한적인데, 어떻게 시스템 콜 수준의 모니터링을 하겠다는 것인가요?
    *   **답변 방향:** 맞습니다. 플랫폼 자체에 직접 접근은 어렵습니다. 하지만 로우코드 앱이 외부 서비스와 통신하기 위해 호출하는 API Gateway, 서비스 간 통신을 제어하는 Service Mesh (e.g., Istio), 또는 컨테이너 기반으로 동작한다면 Sidecar 패턴을 활용하여 네트워크 트래픽과 API 호출 내역을 감시할 수 있습니다. 즉, 앱 내부가 아닌 '앱 주변의 인프라'를 통해 관측성을 확보하는 전략입니다. 제 컨테이너 이상탐지 경험도 커널에서 직접 syscall을 hooking한 것이 아니라, eBPF와 같은 기술을 이용해 커널의 도움을 받아 안전하게 관측한 경험이므로 유사한 접근이 가능하다고 생각합니다.
2.  **질문:** 시민 개발자가 만든 수많은 앱의 정상/비정상 행위를 정의하는 기준(Baseline)을 만드는 것이 현실적으로 가능한가요?
    *   **답변 방향:** 모든 것을 수동으로 정의하는 것은 불가능에 가깝습니다. 그래서 '동적 관측을 통한 이상탐지' 경험이 중요하다고 생각합니다. 초기에는 앱이 사용하는 API, 접근하는 데이터베이스 테이블 등 명시적인 규칙 기반으로 최소한의 통제를 시작합니다. 동시에, 일정 기간 동안 앱의 정상적인 활동 패턴(API 호출 빈도, 데이터 전송량, 접근 시간대 등)을 머신러닝으로 학습하여 기준 모델을 만듭니다. 이 모델에서 크게 벗어나는 이례적인 활동을 '이상 징후'로 탐지하고 알림을 보내는 방식으로 자동화할 수 있습니다.
3.  **질문:** 본인이 생각하는 로우코드와, 직접 코드를 짜는 전통적인 개발 방식의 이상적인 협업 모델은 무엇인가요?
    *   **답변 방향:** 'Core & Edge' 모델을 생각합니다. 기업의 핵심 비즈니스 로직, 대규모 데이터 처리, 고성능이 요구되는 부분은 전문 개발자 그룹이 'Core' 시스템으로 개발하고 안정적으로 운영합니다. 그리고 이 Core 시스템의 기능을 안전한 API 형태로 외부에 노출시킵니다. 그러면 각 현업 부서의 시민 개발자들은 이 API를 레고 블록처럼 활용하여, 자신들의 업무에 필요한 'Edge' 애플리케이션(간단한 보고서 자동화, 데이터 입력 폼 등)을 로우코드로 신속하게 만들어 사용하는 모델입니다. IT 부서는 이 과정에서 API 게이트웨이를 통해 모든 API 사용을 통제하고 모니터링하여 '섀도우 IT'를 방지하고 전체적인 기술 거버넌스를 유지하는 역할을 해야 합니다.

### 10. 지원자 경험 연결 각도 (컨테이너 보안·커널·syscall 이상탐지·인프라 관점에서 엮는 법)
"면접관님, 저는 로우코드/노코드 플랫폼을 단순히 '코딩 안 하고 앱 만드는 툴'로 보지 않습니다. 저는 이것을 **'추상화된 실행 환경(Abstracted Runtime Environment)'**이자, 잠재적 보안 위협을 가진 **'거대한 블랙박스'**로 봅니다. 이는 제가 경험했던 컨테이너와 매우 유사한 속성입니다.

**첫째, '추상화'와 '블랙박스'라는 공통점입니다.** 개발자들은 도커파일(Dockerfile)과 이미지를 통해 애플리케이션을 컨테이너라는 표준화된 상자에 담습니다. 그 내부에서 어떤 OS가 돌고 어떤 라이브러리가 있는지 깊게 신경 쓰지 않아도 어디서든 동일하게 실행됩니다. 로우코드도 마찬가지입니다. 시민 개발자는 GUI를 통해 비즈니스 로직이라는 상자를 만들면, 플랫폼이 알아서 코드를 생성하고 인프라에 배포합니다. 둘 다 내부를 직접 들여다보기 어려운 '블랙박스'이며, 매우 높은 수준으로 추상화되어 있다는 점에서 동일합니다.

**둘째, '내부 관측의 필요성'입니다.** 저는 컨테이너의 구조적 보안 문제를 해결하기 위해, 컨테이너 내부에서 발생하는 시스템 콜(syscall)을 동적으로 관측하여 이상 행위를 탐지하는 연구를 했습니다. 정상적인 웹서버 컨테이너가 갑자기 `execve` 같은 시스템 콜을 호출하여 새로운 프로세스를 실행한다면 이는 명백한 해킹 징후입니다. 마찬가지로 로우코드로 만든 인사관리 앱이 갑자기 외부의 알 수 없는 API 서버로 대량의 데이터를 전송하거나, 재무 관련 데이터베이스 테이블에 접근을 시도한다면 이는 '비정상 행위'일 가능성이 높습니다.

**따라서 저는 로우코드의 확산이 '새로운 차원의 런타임 보안 문제'를 야기할 것이라 확신합니다.** 제가 컨테이너의 시스템 콜을 분석했던 것처럼, 로우코드 앱이 생성하는 네트워크 트래픽, API 호출 패턴, 데이터 접근 로그를 **'인프라 레벨에서'** 동적으로 관측하고 분석하여 이상 징후를 탐지하고 통제하는 접근이 반드시 필요합니다. 로우코드 플랫폼이 제공하는 기능에만 의존하는 것이 아니라, 그 플랫폼이 동작하는 더 낮은 레벨, 즉 인프라 관점에서 보안과 안정성을 확보하는 것입니다.

SSAFY에서 웹 애플리케이션과 시스템 아키텍처 전반에 대한 이해를 넓혀, 단순히 로우코드 플랫폼을 사용하는 것을 넘어, **'안전하고 통제 가능한 로우코드 생태계'를 설계하고 구축하는 인프라 역량을 갖춘 개발자**로 성장하고 싶습니다. 이것이 제가 가진 저수준(low-level) 시스템에 대한 이해와 앞으로 배우게 될 고수준(high-level) 애플리케이션 지식을 융합하여 기여할 수 있는 차별화된 지점이라고 생각합니다."

### 11. PT 적합도 평가
*   **난이도: 상**
    *   **이유:** 단순히 로우코드의 장단점을 나열하는 수준을 넘어, '섀도우 IT', '거버넌스', '런타임 보안' 등 기업 IT의 복잡한 문제를 다뤄야 합니다. 또한, 자신의 경험(컨테이너, 시스템 콜)과 연결 짓기 위해 두 기술 영역 모두에 대한 깊은 이해를 보여줘야 하므로 발표 준비 난이도가 높습니다.
*   **면접관 흥미도: 상**
    *   **이유:** 대부분의 지원자가 로우코드를 '개발 생산성 도구' 정도로만 피상적으로 이해할 가능성이 높습니다. 반면, 이 주제는 로우코드를 '보안'과 '인프라'라는 새로운 관점에서 접근하여 면접관에게 신선한 인상을 줄 수 있습니다. 특히 기술의 이면(단점, 리스크)을 깊이 파고들어 해결책까지 제시하는 구조는 문제 해결 능력을 어필하기에 매우 좋습니다.
*   **차별화 가능성: 상**
    *   **이유:** 지원자의 가장 독창적인 경험인 '컨테이너 시스템 콜 이상탐지'와 직접적으로 연결할 수 있는 최고의 주제 중 하나입니다. "로우코드 앱을 컨테이너처럼 바라보고, API 호출을 시스템 콜처럼 분석하겠다"는 비유와 논리는 다른 지원자가 따라 하기 힘든 강력하고 구체적인 차별화 포인트입니다. 융합형 인재로서의 성장 가능성을 명확하게 보여줄 수 있습니다.
