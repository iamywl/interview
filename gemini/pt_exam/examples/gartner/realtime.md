## 시스템의 맥박에서 비즈니스의 심장으로: 실시간 데이터 처리의 모든 것

### 0. 한 줄 핵심 메시지 / 발표 시간 배분

-   **한 줄 핵심 메시지:** 실시간 데이터 처리는 단순히 빠른 기술이 아니라, 연속적인 시스템 이벤트를 즉각적인 비즈니스 가치로 변환하는 핵심 역량이며, 저는 시스템의 가장 깊은 곳에서 그 경험을 시작했습니다.

### 1. 주제 선정 이유 (면접관의 흥미 포인트 + 지원자 강점과의 연결)

우리가 매일 사용하는 배달 앱의 실시간 위치 추적, 주식 앱의 시세 변동, OTT 서비스의 콘텐츠 추천은 모두 실시간 데이터 처리 기술 위에 있습니다. 이처럼 현대 SW 서비스의 핵심 경쟁력으로 자리 잡은 이 주제는 기술 트렌드에 대한 저의 깊은 관심을 보여줍니다.

특히, 저는 컨테이너 보안을 위해 리눅스 커널에서 발생하는 시스템 콜(syscall)이라는 저수준 이벤트를 실시간으로 추적하고 이상 패턴을 탐지하는 프로젝트를 수행한 경험이 있습니다. 이는 초당 수만 개의 이벤트를 지연 없이 처리해야 하는, 본질적으로 고도의 실시간 스트림 처리 작업이었습니다. 이 경험을 통해 저는 비즈니스 레벨의 실시간 데이터 처리 역시 기술적 원리는 동일하며, 제 경험이 더 넓은 애플리케이션 아키텍처로 확장될 수 있는 강력한 기반이 될 것이라 확신하여 이 주제를 선정했습니다.

### 3. 슬라이드별 핵심 내용 (슬라이드 5~7장, 각 장 제목 + 담을 핵심 bullet 3개 내외)

-   **슬라이드 1: 발표 제목**
    -   시스템의 맥박에서 비즈니스의 심장으로: 실시간 데이터 처리의 모든 것
    -   발표자: OOO
    -   (배경 이미지: 데이터가 흘러가는 추상적인 이미지)

-   **슬라이드 2: 서론 - 데이터, '쌓아두는' 시대에서 '흐르는' 시대로**
    -   **과거(Batch):** 데이터를 모아서, 한 번에, 주기적으로 처리 (예: 월말 정산)
    -   **현재(Real-time):** 데이터가 발생하는 즉시, 연속적으로, 실시간으로 처리 및 반응 (예: 실시간 사기거래 탐지)
    -   **Why Now?** 고객 경험 극대화, 비즈니스 기회 즉시 포착을 위한 필수 기술

-   **슬라이드 3: 본론 1 - 실시간 데이터 처리의 핵심 개념**
    -   **이벤트(Event):** 시스템에서 발생한 모든 사건 (예: '사용자가 버튼을 클릭했다', '온도가 1도 올랐다')
    -   **스트림(Stream):** 시간 순서에 따라 연속적으로 발생하는 이벤트들의 흐름
    -   **이벤트 기반 아키텍처(EDA):** 이벤트의 발생, 처리, 전파를 중심으로 시스템을 구성하는 방식

-   **슬라이드 4: 본론 2 - 대표 기술과 아키텍처**
    -   **(간단한 아키텍처 다이어그램)**
        `Source(데이터 발생) -> Kafka(이벤트 저장/전달) -> Flink(스트림 처리) -> Sink(결과 저장/반영)`
    -   **Apache Kafka:** 대용량 이벤트를 안정적으로 전달하는 '데이터 고속도로' (메시지 큐)
    -   **Apache Flink/Spark Streaming:** 흐르는 데이터를 실시간으로 계산하고 분석하는 '처리 엔진'

-   **슬라이드 5: 본론 3 - 저의 경험: 시스템 콜 스트림 처리**
    -   **주제:** 컨테이너 보안을 위한 시스템 콜 실시간 이상탐지
    -   **개념:** 컨테이너 내부의 모든 동작(시스템 콜)을 '이벤트'로 간주, 실시간으로 스트림을 관측
    -   **결론:** 정상 행위 패턴을 학습 후, 이와 다른 '이상 이벤트'를 실시간으로 탐지. 이는 비즈니스 데이터가 아닌 시스템 데이터로 동일한 실시간 처리 원리를 적용한 사례.

-   **슬라이드 6: 결론 - 도전과제와 저의 기여 방안**
    -   **기술적 과제:** 데이터 유실 및 중복 없는 정확한 처리(Exactly-once), 낮은 지연 시간(Low Latency) 보장
    -   **저의 비전:** 리눅스 커널 수준의 저수준 시스템 이해와 SSAFY에서 배울 애플리케이션/풀스택 개발 역량을 결합
    -   **최종 목표:** 시스템과 서비스를 모두 이해하는 '융합형 개발자'로 성장하여 실시간 데이터 기반의 안정적이고 혁신적인 서비스를 만드는 데 기여

마지막으로, **'이벤트 기반 아키텍처'**입니다. 이벤트를 중심으로 시스템 전체를 설계하는 방식으로, 한 곳에서 이벤트가 발생하면, 그 이벤트를 구독한 다른 시스템들이 알아서 반응하며 독립적으로 동작하는 구조입니다.

(슬라이드 4)
이러한 개념을 구현하기 위한 대표적인 기술과 아키텍처는 다음과 같습니다.

그 다음, **'아파치 플링크'나 '스파크 스트리밍'** 같은 처리 엔진이 이 고속도로를 달리는 데이터를 실시간으로 계산하고 분석합니다. 예를 들어 '최근 5분간 주문량이 급증했는지'를 알아내는 식입니다.

마지막으로, 처리된 결과는 데이터베이스나 사용자 화면 같은 '싱크'로 전달되어 최종적으로 가치를 만들어냅니다.

(슬라이드 5)
저 역시 이러한 실시간 스트림 처리의 원리를 직접 경험한 적이 있습니다. 저는 컨테이너의 보안 취약점을 해결하기 위해, 컨테이너 내부에서 발생하는 모든 **'시스템 콜'**을 하나의 '이벤트'로 보고, 이 이벤트 스트림을 실시간으로 추적하는 프로젝트를 진행했습니다.

시스템 콜은 프로그램이 커널에 무언가를 요청하는 통신 채널로, 초당 수만에서 수십만 개까지 발생합니다. 저는 이 방대한 시스템 콜 스트림에서 정상적인 애플리케이션의 행위 패턴을 학습시켰고, 그 패턴에서 벗어나는 '이상 이벤트'를 실시간으로 탐지해내는 시스템을 개발했습니다.

이는 비즈니스 데이터가 아닌 시스템 데이터라는 점만 다를 뿐, 대용량의 이벤트 스트림을 지연 없이 분석하여 의미 있는 결과를 도출한다는 점에서 실시간 데이터 처리의 본질과 정확히 일치하는 경험이었습니다.

(슬라이드 6)
물론 실시간 데이터 처리에는 어려운 과제들이 많습니다. 데이터를 처리하는 도중 장애가 발생해도, 단 하나의 데이터도 유실되거나 중복 처리되지 않도록 보장하는 것, 그리고 처리 지연 시간을 최대한 낮추는 것이 핵심적인 기술적 난제입니다.

저는 리눅스 커널과 시스템 콜에 대한 깊은 이해를 바탕으로 시스템의 동작 원리를 파악하는 강점을 가지고 있습니다. 여기에 SSAFY의 기본 및 심화 과정을 통해 파이썬 풀스택 개발 역량과 다양한 아키텍처 설계 능력을 더하고 싶습니다.

### 5. 예상 꼬리질문 5개 + 답변 방향 (기술적 깊이가 드러나게, 각 2~3문장)

1.  **질문:** 배치 처리와 스트림 처리의 가장 큰 차이점은 무엇이고, 어떤 경우에 스트림 처리가 반드시 필요한가요?
    -   **답변 방향:** 가장 큰 차이는 '데이터를 바라보는 관점'입니다. 배치는 정해진 크기의 '유한한 데이터 셋'을 처리하는 반면, 스트림은 계속해서 들어오는 '무한한 데이터 스트림'을 처리합니다. 실시간 사기거래 탐지(FDS)나 온라인 게임의 상태 동기화처럼, 데이터 발생과 거의 동시에 즉각적인 반응이 비즈니스적으로 필수적인 경우에 스트림 처리는 선택이 아닌 필수입니다.

2.  **질문:** 발표에서 Kafka를 '데이터 고속도로'라고 표현했는데, 그냥 데이터베이스에 바로 쓰면 안되는 이유가 무엇인가요?
    -   **답변 방향:** 데이터 생산자와 소비자 사이의 '결합(coupling)'을 끊어주기 위함입니다. 만약 모든 서비스가 DB에 직접 데이터를 쓴다면, DB에 부하가 몰리거나 스키마 변경 시 모든 서비스가 영향을 받습니다. 카프카는 중간에서 버퍼 역할을 하며 생산자와 소비자가 서로의 존재나 상태를 몰라도 비동기적으로 데이터를 주고받게 하여, 시스템 전체의 확장성과 안정성을 크게 높여줍니다.

3.  **질문:** Flink와 같은 처리 엔진에서 'Exactly-once' 처리를 보장하는 것이 왜 어렵고, 일반적으로 어떤 원리로 구현되나요?
    -   **답변 방향:** 분산 환경에서 장애는 언제든 발생할 수 있기 때문입니다. 처리 도중 장애가 나면, 복구 후 어디서부터 다시 처리해야 할지 결정하기 어려워 중복(At-least-once)이나 유실(At-most-once)이 발생하기 쉽습니다. 이를 해결하기 위해 플링크는 '분산 스냅샷'과 '트랜잭셔널 아웃풋' 같은 기법을 사용합니다. 주기적으로 모든 오퍼레이터의 상태를 스냅샷으로 저장하고, 장애 발생 시 가장 최근의 성공적인 스냅샷에서부터 복구하여 트랜잭션의 원자성을 보장함으로써 Exactly-once를 구현합니다.

4.  **질문:** 본인의 '시스템 콜 이상탐지' 경험과, 일반적인 '비즈니스 데이터' 스트림 처리의 가장 큰 차이점은 무엇이라고 생각하나요?
    -   **답변 방향:** 데이터의 '정형성'과 '처리 목표'가 가장 큰 차이점입니다. 시스템 콜 데이터는 구조는 일정하지만 발생 빈도가 극도로 높고 개별 이벤트의 가치는 낮은 반면, 비즈니스 이벤트는 구조가 다양하고 개별 이벤트 하나하나가 명확한 의미와 가치를 가집니다. 따라서 시스템 콜 처리는 통계적 패턴 분석과 이상치 탐지에 집중했다면, 비즈니스 데이터 처리는 개별 이벤트의 내용을 분석하고 상태를 변화시키거나 여러 이벤트를 조합(join)하는 등의 더 복잡한 로직이 요구될 것입니다.

5.  **질문:** 만약 SSAFY에서 실시간 데이터 처리와 관련된 프로젝트를 한다면, 어떤 서비스를 만들어보고 싶나요?
    -   **답변 방향:** SSAFY 기본과정에서 배울 웹 개발 지식을 활용하여 '실시간 협업 코드 에디터'를 만들어보고 싶습니다. 여러 사용자의 키 입력 이벤트를 실시간 스트림으로 처리하여 모든 참여자에게 지연 없이 동기화하는 서비스입니다. 이 프로젝트를 통해 웹소켓 통신, 이벤트 스트림 처리, 그리고 충돌 해결 로직(CRDT 등)을 실제로 구현하며 풀스택 서비스 개발 역량을 기르고 싶습니다.

### 6. 지원자 경험 연결 (컨테이너 보안·syscall 동적 관측·Linux 커널·이상탐지 경험을 자연스럽게 엮는 멘트)

(발표 대본 4분 30초경, 또는 꼬리질문 답변 시)
"제가 컨테이너 내부의 시스템 콜 스트림을 분석했던 경험에 비추어 볼 때, 가장 흥미로웠던 점은 데이터 소스가 다를 뿐, 문제를 해결하는 접근 방식이 매우 유사하다는 것이었습니다. 커널에서 올라오는 날 것의(raw) 데이터를 정제하고, 정상 상태를 정의하고, 실시간으로 흐르는 데이터 속에서 패턴을 찾아내는 과정은, 결국 '데이터에서 가치를 찾는' 본질적인 역량이라고 생각합니다. 저는 이 역량을 바탕으로, SSAFY에서 더 넓은 도메인의 문제를 해결하는 개발자로 성장하고 싶습니다."

### 7. 발표 팁 / 흔한 함정 (이 주제 특유의 주의점)

-   **발표 팁:**
    -   자신감 있는 태도로 '저는 이미 이 분야의 한 축(시스템 레벨)을 깊이 경험해봤습니다'라는 뉘앙스를 풍기는 것이 중요합니다.
    -   기술 용어(카프카, 플링크)를 나열하는 데 그치지 말고, 각 기술이 '왜' 필요한지, 아키텍처에서 '어떤 역할'을 하는지를 명확히 설명해야 합니다.
    -   '시스템 콜'과 '비즈니스 이벤트'의 유비쿼터스(ubiquitous)한 연결고리를 강조하여, 단순한 지식 암기가 아닌 깊은 통찰력을 보여주는 것이 차별화 포인트입니다.

-   **흔한 함정:**
    -   기술의 깊이에 매몰되어 너무 어려운 용어를 남발하는 것. 면접관은 지원자의 '커뮤니케이션 능력'도 봅니다. 쉬운 비유(고속도로 등)는 좋지만, 복잡한 비유나 유추는 금물입니다.
    -   실시간 처리를 단순히 '속도' 문제로만 접근하는 것. 속도뿐만 아니라 '정확성(exactly-once)', '안정성', '확장성' 등 다양한 기술적 트레이드오프가 존재함을 인지하고 있음을 보여줘야 합니다.
    -   자신의 경험을 너무 과장하거나 동떨어진 이야기처럼 말하는 것. 발표의 모든 내용은 '그래서 내가 SSAFY에 적합한 인재이고, 이곳에서 성장하고 싶다'는 결론으로 귀결되어야 합니다.
