### 1. 주제 선정 이유 (면접관의 흥미 포인트 + 지원자 강점과의 연결)
제가 이 주제를 선택한 이유는, 단순히 최신 기술 트렌드이기 때문만은 아닙니다. 저는 컨테이너 환경에서 시스템 콜(System Call)을 실시간으로 관찰하여 보안 위협을 탐지하는 프로젝트를 수행한 경험이 있습니다. 이 과정에서 저는 초당 수천 개씩 쏟아지는 커널 수준의 데이터를 지연 없이 처리하고, 이전 데이터와의 연관성을 분석하여 '정상' 상태를 벗어나는 미세한 패턴 변화를 포착해야 했습니다.

이것이 바로 거대한 서비스 환경에서 발생하는 데이터를 다루는 '실시간 스트리밍 처리'의 축소판과 같다고 생각했습니다. 시스템의 가장 낮은 수준에서 데이터의 흐름을 추적하고 분석했던 저의 경험이, 대규모 서비스의 데이터를 다루는 빅데이터 분야, 특히 실시간 처리 영역에서 저만의 독창적인 시각과 문제 해결 능력을 발휘할 수 있는 강력한 무기가 될 것이라 확신하여 이 주제를 선정했습니다.

  - **개념:** 데이터를 저장한 뒤 분석하는 '배치(Batch) 처리'와 달리, 데이터가 발생하는 즉시 혹은 수 초 내의 짧은 시간 안에 연속적으로 처리하는 기술
  - **핵심 특징:**
    - 낮은 지연 시간 (Low Latency)
    - 높은 처리량 (High Throughput)
    - 상태 기반 처리 (Stateful Processing)
  - **처리 모델 비교:** 배치, 마이크로배치, 스트리밍의 차이를 간략한 도식으로 표현

**- [슬라이드 4] 본론 2: 핵심 아키텍처**
  - **데이터 파이프라인:** [데이터 소스] → [수집: Kafka] → [처리: Flink/Spark] → [저장/활용: DB/Dashboard]
  - **아키텍처 모델 1 (Lambda):** 정확성을 위한 배치(Batch) 계층과 속도를 위한 스피드(Speed) 계층을 모두 운영하는 구조. 안정적이지만 복잡함.
  - **아키텍처 모델 2 (Kappa):** 모든 처리를 스트리밍으로 통일한 구조. 단순하고 일관성 있지만, 과거 데이터 전체를 재처리하기 까다로울 수 있음.

**- [슬라이드 5] 본론 3: 저의 경험과 연결**
  - **프로젝트 회고:** '컨테이너 시스템 콜 동적 관측을 통한 이상탐지'
    - 데이터 소스: 커널이 생성하는 초당 수천 개의 `syscall` 로그
    - 처리 엔진: 제가 개발한 `eBPF` 기반 분석 프로그램 (상태 기반 이상 패턴 탐지)
    - 결과 활용: 보안팀에 실시간 알림
  - **경험을 통해 얻은 것:**
    - 상태(State) 관리의 중요성: 단일 시스템 콜이 아닌, 시간의 흐름에 따른 연속된 호출 패턴 분석의 필요성 체감
    - 저지연 처리의 어려움: 커널과 사용자 공간 사이의 데이터 전송 병목 현상을 해결하며 얻은 성능 최적화 경험

**- [슬라이드 6] 결론: 융합형 개발자를 향한 비전**
  - **요약:** 실시간 스트리밍 처리는 저의 시스템 레벨 경험을 서비스 레벨로 확장할 수 있는 최적의 분야입니다.
  - **SSAFY에서의 목표:**
    - **기본과정:** Python, 알고리즘 역량을 강화하여 대용량 데이터를 다룰 기초 체력 확보
    - **심화과정:** 웹 풀스택 기술(Django, Vue.js)을 익혀, 데이터 처리부터 서비스 제공까지 전 과정을 아우르는 프로젝트 수행
  - **최종 포부:** 시스템 인프라의 동작 원리를 이해하는 강점을 살려, 안정적이고 효율적인 실시간 데이터 서비스를 설계하고 구현하는 '융합형 개발자'로 성장하겠습니다.

혹시 온라인 쇼핑을 할 때, 방금 본 상품과 비슷한 상품이 바로 추천되는 경험을 해보셨나요? 혹은, 카드 부정사용이 의심된다며 몇 초 만에 문자를 받아보신 적은 없으신가요?

이 모든 것이 바로 '실시간 데이터 처리' 기술 덕분입니다. 이제 기업들은 어제의 데이터를 분석해서 내일의 전략을 짜는 것만으로는 부족합니다. 데이터가 발생하는 바로 그 순간, 가치를 찾아내고 즉각적으로 행동해야만 경쟁에서 살아남을 수 있습니다.

저는 리눅스 커널 수준에서 발생하는 데이터를 실시간으로 관찰하며 시스템의 이상 징후를 탐지하는 프로젝트를 수행했습니다. 이 경험을 통해, 저는 실시간 처리의 중요성을 피부로 느꼈고, 이 기술을 더 큰 서비스 스케일로 확장해보고 싶다는 강한 동기를 갖게 되었습니다.

(슬라이드 3 전환)
그렇다면 실시간 스트리밍 처리란 정확히 무엇일까요?
기존의 '배치 처리'가 데이터를 한곳에 모아놨다가 한 번에 처리하는 방식이라면, '스트리밍 처리'는 데이터가 끝없이 흘러들어오는 강물과 같습니다. 이 강물을 막지 않고, 흐르는 상태 그대로 분석하고 처리하는 기술입니다.

이 기술의 핵심 특징은 세 가지입니다. 첫째, 데이터 발생부터 처리까지 걸리는 시간이 매우 짧은 '낮은 지연 시간'. 둘째, 대규모 데이터를 막힘없이 처리하는 '높은 처리량'. 그리고 마지막으로, 단순히 개별 데이터를 보는 것을 넘어, 이전 데이터와의 연관성을 기억하고 분석하는 '상태 기반 처리'입니다.

(슬라이드 4 전환)
이러한 스트리밍 처리는 보통 다음과 같은 파이프라인 구조를 가집니다. 먼저, 서비스 곳곳에서 발생하는 데이터를 '카프카'와 같은 시스템을 통해 중앙으로 안전하게 수집합니다. 그리고 '아파치 스파크'나 '플링크' 같은 처리 엔진이 이 데이터들을 실시간으로 분석합니다. 마지막으로 그 결과를 데이터베이스에 저장하거나, 사용자가 보는 대시보드에 즉시 시각화해줍니다.

이 파이프라인을 구성하는 대표적인 아키텍처로 '람다'와 '카파'가 있습니다. 람다 아키텍처는 데이터의 정확성을 위해 전통적인 배치 처리 방식과 빠른 처리를 위한 스트리밍 방식을 둘 다 사용하는, 안정적이지만 조금 복잡한 구조입니다. 반면 카파 아키텍처는 "모든 것은 스트림이다"라는 철학 아래, 모든 데이터 처리를 스트리밍으로 통일하여 구조를 단순화한 방식입니다. 최근에는 카파 아키텍처가 많은 주목을 받고 있습니다.

(슬라이드 5 전환)
이 지점에서 저는 제가 수행했던 프로젝트를 다시 떠올렸습니다. 저는 컨테이너의 보안 취약점을 해결하기 위해, 컨테이너 내부에서 발생하는 모든 시스템 콜을 실시간으로 추적하는 이상탐지 시스템을 개발했습니다.

다시 보니, 이 프로젝트는 완벽한 실시간 스트리밍 처리 파이프라인의 축소판이었습니다. 커널이 뱉어내는 시스템 콜 로그가 바로 '데이터 소스'였고, 제가 만든 분석 프로그램이 '처리 엔진', 그리고 보안팀에 보내는 알림이 최종 '결과'였던 셈입니다.

이 경험을 통해 저는 두 가지를 깊이 깨달았습니다. 첫째, '상태 관리'가 정말 중요하다는 것입니다. 예를 들어, 해커가 '파일을 열고(open)', '내용을 읽고(read)', '네트워크로 전송(send)'하는 일련의 과정을 포착하려면, 단순히 각각의 시스템 콜을 보는 것만으로는 부족합니다. 특정 프로세스가 어떤 순서로 시스템 콜을 호출했는지, 그 '상태'와 '문맥'을 기억하고 있어야만 정확한 탐지가 가능했습니다. 둘째, 커널에서 사용자 프로그램으로 데이터를 넘기는 과정에서 발생하는 미세한 지연도 전체 시스템의 성능을 크게 좌우한다는 것을 깨달으며, 저지연 처리의 중요성과 어려움을 직접 해결해 본 경험이 있습니다.

(슬라이드 6 전환)
저는 시스템의 가장 깊은 곳에서 데이터의 흐름을 다뤄본 이 경험이 저만의 큰 자산이라고 생각합니다. 이제 저는 SSAFY에서 한 단계 더 나아가고 싶습니다.

기본과정에서는 파이썬과 알고리즘 역량을 갈고닦아, 대용량 데이터를 효율적으로 다룰 수 있는 탄탄한 기초 체력을 기르겠습니다. 그리고 심화과정에서는 Django, Vue.js 같은 풀스택 웹 기술을 배워, 제가 분석한 데이터를 사용자에게 가치 있는 정보로 전달하는 서비스까지 제 손으로 직접 구현해보고 싶습니다.

시스템 인프라에 대한 이해를 바탕으로, 안정적이고 효율적인 데이터 서비스를 설계하고 개발하는 '융합형 개발자'. 이것이 제가 SSAFY를 통해 이루고 싶은 저의 모습입니다.

### 5. 예상 꼬리질문 5개 + 답변 방향 (기술적 깊이가 드러나게)

**1. Q: "실시간 스트리밍에서 '상태(State) 기반 처리'가 왜 중요하고, 기술적으로 어떤 어려움이 있는지 본인의 경험을 바탕으로 설명해주세요."**
   - **A:** 상태 기반 처리는 단편적인 이벤트가 아닌, 시간의 흐름 속에서 발생하는 '행위'와 '문맥'을 이해하기 위해 필수적입니다. 제가 개발한 시스템 콜 이상탐지 시스템에서, '파일을 연다'는 `open` 시스템 콜 자체는 정상 행위입니다. 하지만 '중요 설정 파일을 연 직후', '외부로 나가는 네트워크 소켓을 연다'는 `socket` 콜이 발생했다면 이는 정보 유출 시도일 수 있습니다. 이처럼 이전 상태를 기억하지 못하면 유의미한 분석이 불가능합니다. 기술적으로는, 분산 환경에서 수많은 서버에 걸쳐 이 '상태'를 일관성 있게 유지하고, 특정 서버에 장애가 발생해도 상태 정보가 유실되지 않도록 보장하는 것이 가장 큰 어려움입니다. 이를 위해 아파치 플링크 같은 엔진은 고도화된 체크포인팅 및 상태 백엔드 기술을 사용합니다.

**2. Q: "아파치 플링크(Flink)와 스파크 스트리밍(Spark Streaming)의 근본적인 차이는 무엇이며, 지원자라면 어떤 상황에서 각각을 선택할 것 같나요?"**
   - **A:** 가장 근본적인 차이는 처리 모델에 있습니다. 플링크는 이벤트 하나하나를 도착하는 즉시 처리하는 '네이티브 스트림' 처리 엔진입니다. 반면, 스파크 스트리밍은 짧은 시간(예: 1초) 동안 들어온 데이터를 작은 묶음, 즉 '마이크로배치'로 만들어 처리합니다. 이 차이 때문에 일반적으로 플링크가 더 낮은 지연 시간과 더 정교한 시간 기반(event-time) 처리를 보장합니다. 저라면, 금융 거래나 공장 설비의 위험 감지처럼 이벤트 발생 순서와 수 밀리초(ms)의 지연 시간이 매우 중요한 업무에는 플링크를, 기존에 스파크(하둡) 생태계를 이미 활발히 사용 중이고, 배치 작업과 스트리밍 작업을 통합 관리하는 것이 더 중요한 환경이라면 스파크 스트리밍을 고려할 것입니다.

**3. Q: "카파 아키텍처가 람다에 비해 구조가 단순하다는 장점이 있지만, 만약 전체 데이터를 재처리해야 할 경우 어떻게 해야 할까요? 이 단점을 어떻게 극복할 수 있을까요?"**
   - **A:** 좋은 지적이십니다. 카파 아키텍처의 주된 과제 중 하나가 바로 모든 과거 데이터에 대한 재처리입니다. 이를 해결하기 위해, 데이터 소스인 카프카 같은 메시지 큐의 데이터 보존 기간을 충분히 길게 설정하는 것이 일반적인 접근법입니다. 즉, 카프카를 단순한 큐가 아닌 '데이터베이스'처럼 활용하는 것입니다. 만약 분석 로직에 변경이 생겨 전체 데이터를 재처리해야 한다면, 카프카에 저장된 가장 오래된 데이터부터 다시 읽어오는 새로운 스트리밍 잡(job)을 실행하면 됩니다. 이렇게 하면 람다 아키텍처의 배치 계층과 유사한 효과를 스트리밍 패러다임 안에서 구현할 수 있습니다.

**4. Q: "본인이 수행한 시스템 콜 탐지 프로젝트를 1000대의 서버 환경으로 확장해야 한다면, 아키텍처를 어떻게 변경하시겠습니까?"**
   - **A:** 현재의 단일 노드 기반 아키텍처는 절대 불가능할 것입니다. 1000대 규모로 확장하기 위해, 먼저 각 서버 노드에는 `eBPF`나 `auditd`를 이용한 경량 데이터 수집 에이전트만 배치하겠습니다. 이 에이전트들은 시스템 콜 로그를 생성 즉시 중앙의 '아파치 카프카' 클러스터로 전송합니다. 그 다음, '아파치 플링크' 클러스터를 구성하여 카프카로부터 데이터를 받아 분산 처리하도록 설계하겠습니다. 이렇게 하면 데이터 수집, 전송, 분석의 각 단계가 분리되어 수평적으로 확장(scale-out)이 가능해지고, 특정 분석 서버에 장애가 나도 전체 시스템이 멈추지 않는 안정성을 확보할 수 있습니다. 이는 제가 SSAFY에서 프로젝트를 통해 꼭 구현해보고 싶은 아키텍처입니다.

**5. Q: "실시간 처리에서 데이터가 유실되거나 순서가 뒤바뀌는 문제는 어떻게 대응해야 할까요? (Exactly-once, At-least-once 등)"**
   - **A:** 데이터 처리 보장 수준(Processing Guarantee)은 실시간 시스템의 신뢰도를 결정하는 핵심 요소입니다. 'At-least-once(최소 한 번 처리)'는 데이터 유실은 없지만 중복 처리가 발생할 수 있고, 'Exactly-once(정확히 한 번 처리)'는 중복도 유실도 없는 가장 높은 수준의 보장입니다. 제가 개발했던 시스템 콜 분석에서는 중복 탐지는 괜찮지만 유실은 치명적이므로 'At-least-once'를 목표로 했습니다. 하지만 금융 거래와 같은 시스템에서는 'Exactly-once'가 필수적입니다. 이를 구현하기 위해 카프카, 플링크 같은 시스템들은 '트랜잭셔널(Transactional) 전송'과 '2단계 커밋(Two-phase commit)' 같은 정교한 메커니즘을 사용합니다. 이를 통해 데이터 소스부터 처리 엔진, 최종 결과 저장까지 전 과정에 걸쳐 데이터의 흐름을 원자적(atomic)으로 관리하여 장애 발생 시에도 데이터 정합성을 보장합니다.

### 6. 지원자 경험 연결 (컨테이너 보안·syscall 동적 관측·Linux 커널·이상탐지 경험을 자연스럽게 엮는 멘트)

"저는 단순히 빅데이터 기술 목록을 나열하는 것이 아니라, 제가 직접 부딪히고 해결했던 경험에 기반하여 이 분야를 이해하고 있습니다. 리눅스 커널 위에서 시스템 콜의 흐름을 추적하며 '상태'를 관리하고, 저지연 처리를 위해 애썼던 경험은, 대규모 분산 환경에서 데이터를 다룰 때 어떤 문제들이 발생할 수 있고, 왜 카프카 같은 메시지 큐와 플링크 같은 분산 처리 엔진이 필요한지에 대한 깊은 공감과 직관을 주었습니다. 남들이 보기엔 다른 분야일 수 있지만, 저에게는 '시스템의 맥박'을 듣는다는 본질은 같으며, 관찰 대상이 커널에서 서비스 데이터로 확장된 것이라 생각합니다. 이 연결고리가 바로 제가 이 분야에 기여할 수 있는 차별화된 포인트라고 확신합니다."

### 7. 발표 팁 / 흔한 함정 (이 주제 특유의 주의점)

- **발표 팁:**
    1.  **'나의 언어'로 설명하기:** 스파크, 카프카, 플링크 같은 기술 용어를 단순히 나열하지 말고, "왜 이 기술이 필요한가?"를 자신의 경험에 빗대어 설명해야 합니다. "시스템 콜이 초당 수만 개씩 쏟아지는 걸 보니, 이걸 한 곳으로 모아주는 버퍼와 같은 역할이 꼭 필요하겠다고 느꼈습니다. 카프카가 바로 그런 대규모 환경에서의 버퍼 역할을 해줍니다." 와 같이 설명하면 훨씬 진정성 있습니다.
    2.  **자신감 있는 태도:** 시스템 커널과 같은 로우레벨(low-level) 경험은 일반적인 신입 지원자들이 갖기 힘든 매우 강력한 무기입니다. 이 경험에 대한 자부심을 바탕으로, "나는 이 문제를 이런 관점에서 다르게 볼 수 있다"는 자신감 있는 태도를 유지하는 것이 중요합니다.
    - **자신을 '융합형 인재'로 포지셔닝:** 발표 내내 '커널 경험'과 '서비스(애플리케이션) 개발 의지'를 연결하는 멘트를 반복하여, 두 분야를 모두 이해하고 연결할 수 있는 인재라는 인상을 심어주는 것이 핵심입니다.

- **흔한 함정:**
    1.  **기술 백과사전식 발표:** 각 기술의 정의와 특징을 나열하는 데 그치면, 지원자가 정말 이 기술을 이해했는지, 왜 이 주제를 골랐는지 알 수 없습니다. 철저히 '그래서 이 기술이 어떤 문제를 해결하는가?'와 '내 경험과 어떻게 연결되는가?'에 초점을 맞춰야 합니다.
    2.  **경험과 주제의 분리:** 발표 초반에만 자기 경험을 언급하고, 본론에서는 완전히 동떨어진 기술 얘기만 하는 것이 최악의 시나리오입니다. 본론의 각 단계(개념, 아키텍처, 기술)마다 "이 부분은 제 프로젝트의 OOO와 유사합니다" 혹은 "제 경험에 비추어볼 때 이 기술은 OOO 때문에 중요합니다" 와 같이 계속해서 연결고리를 만들어줘야 합니다.
